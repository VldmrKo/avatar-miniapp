# Аватар — мини-приложение для MAX

Бот с мини-приложением: человек даёт фото или видео, голос и текст, получает
в чат говорящего аватара. Модель — MiniMax H3, вызывается через `avatar-core`.

Режимов три:

| режим | вход | что происходит |
|---|---|---|
| Cartoon avatar | фото, голос, реплика | Kandinsky рисует портрет, H3 его оживляет |
| Аватар по фото | фото, голос, реплика | H3 оживляет фото как есть |
| Аватар по видео | видео, реплика | H3 берёт из видео и внешность, и голос |

**Два входа, один движок.** Тот же сценарий целиком работает в переписке
с ботом: он спрашивает по шагам и не требует ни разу выйти из чата. Это не
дубль ради дубля — MAX не отдаёт вебвью микрофон (`NotAllowedError` при
живых `mediaDevices`, то есть спросить разрешение некому), и «записать свой
голос» из окна означает шесть действий с тремя переключениями контекста.
В переписке их ноль. Сценарий живёт в `dialog.py` и ничего не знает ни про
maxapi, ни про HTTP — поэтому проверяется тестами целиком.

Рисованный режим единственный ходит в два сервиса. Без `KANDINSKY_BASE_URL`
и `KANDINSKY_TOKEN` он просто не предлагается — кнопки в окне не будет,
остальные два работают как работали.

## Запуск локально

```
run-local.bat            первый раз сам создаст .venv и поставит зависимости
test.bat                 тесты, полторы минуты, без сети и без модели
npm install jsdom        разово: включает проверку самого окна
```

Без jsdom проверка интерфейса пропускается, остальные идут как обычно.

Окно открывается на <http://127.0.0.1:8081>. Вебвью MAX локально не откроется:
ему нужен HTTPS и адрес, привязанный в `business.max.ru/self`. Поэтому локально
проверяется логика, а интерфейс — только на телефоне после выкладки.

Секреты — в `%USERPROFILE%\.avatars\secrets.env`, шаблон в
`../avatar-core/.env.example`. Для локальной работы нужны:

```
MINIAPP_DEV_ALLOW_UNSIGNED=1
MINIAPP_CHAT_ENABLED=0
```

Первый пускает запросы без подписи (вне MAX её взять негде).
Второй гасит чат-часть: **один токен = один процесс long polling**, и если
бот уже работает на сервере, два процесса поделят апдейты пополам.

## Что где

| файл | о чём |
|---|---|
| `__main__.py` | точка входа: веб-сервер и чат-часть в одном процессе |
| `initdata.py` | проверка подписи — единственное, что стоит между ключом и curl |
| `jobs.py` | очередь, одна задача на человека, жизнь после перезапуска |
| `chat.py` | события мессенджера, доставка результата, обратная связь |
| `dialog.py` | сценарий в переписке: шаги, вопросы, состояние на диске |
| `api.py` | эндпоинты и разбор загрузок |
| `prepare.py` | подготовка входов и все отказы, которые видит человек |
| `text.py` | ударения по словарю, промпты всех трёх режимов, стиль рисовки |
| `generate.py` | боевая генерация: Kandinsky рисует, H3 оживляет |
| `inbox.py` | голос и видео, присланные боту в чат |
| `maxcompat.py` | подпорка под обновления, которые maxapi не разбирает |
| `static/` | окно: три экрана на ванильном JS |

## Три решения, которые не надо переигрывать

**Результат уходит в чат всегда.** Окно можно закрыть в любой момент, и
догнать его нечем: ни push, ни переоткрытия в API MAX нет. Показ в окне —
приятный дубль, доставка — чат.

**Счётчик текста в секундах, а не в символах.** Модель заполняет речью всё
время ролика, а ролик не длиннее 15 секунд. Ограничивает именно длительность,
и человеку понятнее «≈ 8 с из 14», чем «120 из 170».

**Генерация подставляется снаружи.** Боевой режим включается сам, как только
в секретах есть `H3_BASE_URL` и `H3_API_KEY`; без них поднимается заглушка на
двадцать секунд и об этом пишется в лог. Принудительно вернуть заглушку —
`MINIAPP_USE_STUB=1`. Весь путь окно ↔ чат отлаживается, не тратя генерации.

**Готовые голоса лежат в данных, а не в репозитории.** Это записи живых
людей, а репозиторий публичный. Положите `*.wav` в `<данные>/voices/`
(на сервере это `/var/lib/avatar-miniapp/voices/`), подписи по желанию
в `voices.yaml` рядом:

```yaml
anya:    {title: "Аня",    note: "женский, спокойный"}
sergey:  {title: "Сергей", note: "мужской, деловой"}
```

Список строится по факту наличия файлов, править код для нового голоса
не нужно.

## Что выяснилось про MAX по дороге

Всё это стоило по половине дня и в документации не написано.

**Микрофон окну не дают.** `getUserMedia` падает с `NotAllowedError` ещё
до вопроса о разрешении. Камеру файловый выбор открывает только для фото,
`capture` ничего не меняет.

**Голосовые ботам не отдаются.** По ним прилетает пустое событие:
`{"timestamp":…, "user_locale":"ru", "update_type":"message_created"}` —
ни тела, ни ссылки. А видео приезжает целиком, со ссылкой на CDN. Поэтому
«записать голос» у нас значит «снять короткий ролик», а звук берём из него.

**Голос и видео приходят одинаково** — типом `file` и ссылкой
`getfile?rq=…` без расширения. Различаем по содержимому, а не по имени.

**Кнопки уезжают одним вложением** `inline_keyboard`, ряды лежат внутри
`ButtonsPayload`. Список списков библиотека принимает молча и падает уже
при отправке: `'list' object has no attribute 'model_dump'`.

**`OpenAppButton` ищет адрес в реестре MAX** по точному совпадению и
отвечает `Link not found with pk = LinkPK{name=…}`, если не нашёл. В запасе
глубокая ссылка `max.ru/<бот>?startapp=<экран>` — работает всегда.

**maxapi молча выбрасывает** обновления, которые не разобрал, печатая
«Получен неизвестный тип обновления». Тип при этом известный, не подошло
какое-то поле. `maxcompat.py` перехватывает такие и показывает сырое
событие целиком.
